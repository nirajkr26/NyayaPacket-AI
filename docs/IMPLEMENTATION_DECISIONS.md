# NyayaPacket AI — Implementation Decisions & Architectural Reconciliation

## 1. Context & Purpose

The initial repository documentation (`db.md`, `api.md`, `ui.md`, `system_architecture.md`, `nyayapacket.md`) provided a solid conceptual foundation, but contained several cross-document variations, legacy references (such as Clerk and local Tesseract/Whisper), and underspecified authorization nuances. 

This document formally records all key architectural decisions, reconciles inconsistencies between the reference files, and establishes the authoritative engineering contract for the NyayaPacket AI platform.

---

## 2. Architectural Decisions & Reconciliations

### 2.1 Authentication & Identity Management

* **Discrepancy in Reference Docs**: `db.md` and `api.md` referenced Clerk (`clerkUserId`, Clerk webhooks, Clerk JWT verification).
* **Master Specification Requirement**: Mandatory adoption of **Better Auth** (provided by Neon / Neon Auth) using `AUTH_URL` and `JWKS_URL`.
* **Decision**:
  1. Replace all Clerk references with **Better Auth (Neon Auth)**.
  2. The Prisma `User` schema replaces `clerkUserId` with:
     ```prisma
     authUserId String @unique // Neon Auth / Better Auth user ID (`sub`)
     ```
  3. **Decoupling Identity from Authorization**:
     - Better Auth answers: *“Who is this user?”*
     - PostgreSQL answers: *“What can this user do?”*
     - User roles (`CITIZEN`, `LAWYER`, `ADMIN`), account statuses (`ACTIVE`, `SUSPENDED`, `DEACTIVATED`), and lawyer verification statuses (`PENDING`, `APPROVED`, `REJECTED`, `SUSPENDED`) are stored **strictly in PostgreSQL**.
     - Token claims from the frontend are never trusted for authorization.
  4. **Verification & Synchronous Provisioning**:
     - Express API middleware verifies incoming Bearer JWTs against the Neon Auth JWKS endpoint (`JWKS_URL`) using cryptographic libraries (`jose`).
     - On the first authenticated request (e.g., via `GET /auth/me`), an idempotent on-demand provisioning hook ensures the corresponding PostgreSQL `User` record exists.
     - Webhooks serve as an auxiliary, asynchronous synchronization layer, but are not relied upon as the single point of failure.

### 2.2 OCR, Multimodal Vision & Speech-to-Text

* **Discrepancy in Reference Docs**: `system_architecture.md` suggested local Tesseract OCR and local Whisper models.
* **Master Specification Requirement & Environment**: Use Gemini Multimodal Vision and Deepgram Speech-to-Text via cloud APIs (with environment keys `GEMINI_API_KEY` and `DEEPGRAM_API_KEY`).
* **Decision**:
  1. **Document Text & Scanned Receipt Ingestion**:
     - Use **Google Gemini Multimodal Vision** (with provider fallback to OpenAI Vision) to inspect images, WhatsApp screenshots, UPI receipts, and scanned documents.
     - For pure text-based PDFs, extract text deterministically using lightweight PDF parsers (`pdf-parse`) before falling back to Vision LLMs. This minimizes latency and cost.
     - Tesseract is eliminated from the runtime stack, avoiding heavy native C++ dependencies and inconsistent OS binary distributions.
  2. **Voice Recording & Audio Transcription**:
     - Use the **Deepgram Nova-2 API** for all citizen audio recordings and voice notes.
     - Deepgram provides industry-leading transcription accuracy, native handling of Indian accents, multi-language code-switching (Hinglish/English/Hindi), and diarization timestamps.
  3. **Provider Abstraction Pattern**:
     - Implement clean provider interfaces (`IVisionProvider`, `IAudioTranscriber`, `ILLMProvider`) in `server/src/services/ai/providers/`.
     - Business logic interacts only with the abstract interfaces, allowing seamless switching or fallback between Gemini and OpenAI.

### 2.3 Storage Architecture & Evidence Integrity

* **Discrepancy in Reference Docs**: Generic S3/Cloudflare R2 references with unspecified authorization flow.
* **Master Specification Requirement**: Neon-provided private S3-compatible object storage (`AWS_ENDPOINT_URL_S3`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION`) with presigned URLs.
* **Decision**:
  1. **Strictly Private Bucket**: No bucket is ever configured with public read access.
  2. **Two-Phase Presigned Upload**:
     - **Phase 1**: Client requests presigned upload URL via `POST /api/v1/cases/:id/evidence/upload-url` providing file metadata (filename, MIME type, file size).
     - **Phase 2**: Client uploads directly from browser to S3 via HTTP `PUT`.
     - **Phase 3**: Client calls `POST /api/v1/cases/:id/evidence/complete` passing the computed SHA-256 digest. Backend validates the uploaded S3 object metadata and persists the `Evidence` record.
  3. **Secure Download Gates**:
     - Evidence files and PDF packets are retrieved solely via short-lived (15-minute TTL) presigned `GET` URLs generated by the backend.
     - Every download request must pass centralized resource-level authorization (`canAccessCase(user, caseId, 'VIEW_EVIDENCE')`).
  4. **Cryptographic SHA-256 Semantics**:
     - SHA-256 verifies tamper-resistance and consistency between stored content and generation logs.
     - It does not constitute independent legal proof of document authenticity, which is explicitly noted in the UI and documentation.

### 2.4 Background Queues & Asynchronous Processing

* **Discrepancy in Reference Docs**: Generic Redis/BullMQ with ambiguous connection specs.
* **Master Specification Requirement**: Upstash Redis with TLS (`rediss://`) via BullMQ in a modular monolith.
* **Decision**:
  1. Connect BullMQ using the Upstash Redis TLS connection string (`REDIS_URL`).
  2. Structure the background worker as a separate runnable process (`bun run worker.ts`) within the same backend codebase (`server/`).
  3. Workers share Prisma database models, Zod validation schemas, and AI service providers with the Express server.
  4. Implement dedicated queues with bounded exponential backoff:
     - `evidence-processing-queue` (OCR & Deepgram transcription)
     - `ai-analysis-queue` (Gemini case summarization & timeline extraction)
     - `pdf-generation-queue` (Puppeteer PDF rendering)
     - `notification-queue` (In-app alerts & emails)
  5. APIs accepting asynchronous requests return HTTP `202 Accepted` with a job tracking payload.

### 2.5 Centralized Resource-Level Authorization & Access Grants

* **Discrepancy in Reference Docs**: `db.md` had basic boolean flags in `AccessGrant` (`canViewSummary`, `canViewEvidence`, `canDownload`), while `system_architecture.md` detailed granular permission scopes.
* **Decision**:
  1. Implement both backward-compatible boolean columns in Prisma and structured permission scopes in code:
     - Scopes: `VIEW_CASE_SUMMARY`, `VIEW_TIMELINE`, `VIEW_EVIDENCE`, `DOWNLOAD_EVIDENCE`, `VIEW_VERIFICATION_HISTORY`, `COMMENT_ON_CASE`, `REQUEST_INFORMATION`, `MANAGE_ACTION_ITEMS`.
  2. Centralize all checks in a dedicated authorization service:
     ```typescript
     async function canAccessCase(params: {
       user: User;
       caseId: string;
       requiredPermission: PermissionScope;
     }): Promise<{ allowed: boolean; reason?: string }>;
     ```
  3. **Immediate Revocation**: Access grants check `revokedAt IS NULL` and `expiresAt > NOW()` on every single request. Caching grant decisions across requests is prohibited.
  4. **Tenancy Isolation**:
     - Citizens can access only their own cases (`ownerId === user.id`).
     - Approved Lawyers can access only cases with an active, non-expired, non-revoked `AccessGrant`.
     - Pending/Rejected/Suspended Lawyers are blocked unconditionally.

### 2.6 Admin Privacy Safeguards

* **Discrepancy in Reference Docs**: Ambiguity regarding whether Platform Admins have superuser visibility into citizen documents.
* **Master Specification Requirement**: Admins must **not** automatically receive unrestricted access to citizen legal documents or case contents.
* **Decision**:
  1. The Admin portal and APIs expose **only metadata**: case numbers, case categories, status history, timestamps, lawyer verification submissions, and system audit logs.
  2. Evidence download endpoints (`/api/v1/cases/:id/evidence/:evidenceId/download`) reject Admin requests by default unless an emergency audit override with mandatory justification is enacted.
  3. Any administrative override creates an indelible `AuditLog` entry flagged with high severity.
  4. Admins cannot be created via public signups; only via a controlled bootstrap CLI script (`bun run seed:admin`).

---

### 2.7 PDF Generation & Tamper Evidence

* **Decision**:
  1. Use **Puppeteer** with headless Chromium to render HTML/CSS templates into high-fidelity PDF documents.
  2. Each generated packet is versioned incrementally (`version: 1, 2, ...`).
  3. The PDF includes:
     - Official Case Header & Unique Packet Reference Number.
     - Disclaimer Banner stating assistance-only nature.
     - Structured Case Summary & Parties Involved.
     - Chronological Timeline with explicit Source Reference IDs.
     - Evidence Index with file hashes and descriptions.
     - Missing Information & Recommended Advocate Questions.
     - Citizen Verification Stamp & Audit Checksum.
  4. The generated PDF binary is hashed with SHA-256, saved to private S3, and stored in `PacketGeneration`.

---

### 2.8 Runtime, Toolchain & Frontend Tech Stack

* **Decision**:
  1. **Runtime**: **Bun** (v1.2+) is the standard runtime and package manager for the backend and developer tooling.
  2. **Backend**: Express.js with TypeScript in strict mode, Prisma ORM for PostgreSQL.
  3. **Frontend**:
     - React 19 + TypeScript + Vite.
     - Tailwind CSS (v4) + shadcn/ui component architecture.
     - Lucide React for iconography.
     - React Router v7 for client-side routing and protected layout boundaries.
     - TanStack Query v5 for API caching, mutation lifecycles, and optimistic updates.
     - Zod + React Hook Form for client-side schema validation matching backend Zod contracts.
     - `@better-auth/react` for seamless authentication session management.

## 3. Summary of Specification Reconciliations

| Domain | Initial Docs Reference | Master Specification Decision | Rationale |
| :--- | :--- | :--- | :--- |
| **Auth Provider** | Clerk (`clerkUserId`) | Better Auth / Neon Auth (`authUserId`) | Native integration with Neon PostgreSQL; open standards JWKS verification via `jose`. |
| **Vision / OCR** | Tesseract OCR | Google Gemini Multimodal Vision API | Superior understanding of unstructured receipts, Hindi/English invoices; zero C++ server dependencies. |
| **Audio Transcription** | Local Whisper model | Deepgram Nova-2 API | Accurate Indian accent transcription, speed, diarization, low server resource overhead. |
| **Object Storage** | Generic S3 / Cloudflare | Neon Private S3 Object Storage | Direct compatibility with AWS SDK v3, private bucket with presigned URLs. |
| **Queue Broker** | Local Redis | Upstash Redis TLS (`rediss://`) | Managed serverless Redis with TLS; reliable for distributed BullMQ jobs. |
| **Admin Privacy** | Superuser read-all | Metadata-only by default; strict audit on override | Confidentiality of citizen legal records; zero trust architecture. |
| **Permission Model** | 3 boolean flags | Boolean columns + granular `PermissionScope` enums | Fine-grained access control on comments, action items, evidence, and packets. |
